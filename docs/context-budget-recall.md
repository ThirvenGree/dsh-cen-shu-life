# 共用上下文预算与精确取回

生活、独处和主动进行继续共用每轮上下文编排。此次增加的是可以核对版本、分页读取的本轮资料快照，以及窗口不足时与既有压缩引擎的衔接。

## 本轮如何选择与分配

三个插件通过生活插件提供的 `cenShuLifeShared.assembleBudget`、`budgetContext` 汇集资料。嵌套的组装监听器先收齐下游内容，再由最外层进行一次预算规划，避免三方各自占满剩余窗口。

Gemini 根据本轮话题、任务和资料摘录，返回：

- `allocations`：生活、独处、主动进行各自建议使用的 token 数与理由；不要求按固定比例分配，也不要求用满窗口。
- `order`：建议纳入的可选资料编号及顺序；无关项可以不选。
- `recall`：暂不展开的条目，以及“遇到什么问题时值得读取”的条件线索。它只是提供可取回的证据入口，不是执行命令，也不强迫角色回忆。
- `reason`：本轮整体分配的理由。

程序保留必需内容，并使用当前模型窗口、回复预留、已有历史、其他提示与工具定义检查可用空间。目录提示和条件线索本身也计入采用量，不能在模型给出的预算之外无限追加。

这里的 token 数是本地估算，不等同于提供方最终计费量。设置状态同时保留本轮估算与可获得的宿主使用回执。规划期间历史增长时，会再次核算可用空间；如果模型路由在规划中改变，会要求按新模型重新组装。

语义模型关闭、失败或退避时，不把失败视为有效的模型决定。当前降级方式是在空间允许时保留各来源最多一项可选资料，并给精确取回入口留出空间；窗口尚未核实时只交还必需内容。降级原因会显示在预算状态里。

## 精确取回代替空泛提示

预算层在决定采用哪些内容时，会保存三方此次提交的文字，包括未注入的可选项。保存的是**本轮传入预算层的精确文字**，不是对所有长期记忆和原始文件的完整备份。

空间允许时，上下文会包含 `snapshotId`、`version` 和只读工具入口；Gemini 选出的条件线索会附上对应的 `itemId`。如果空间连目录都容不下，目录可以不注入，已注册工具仍可查询当前调用会话的最新快照。

先列出目录：

```json
{"action":"catalog"}
```

工具为 `censhu_context_recall`。目录支持 `query` 关键词、`offset` 和 `limit`，每页最多 12 项。返回条目包含来源、所属插件、条目编号、摘录、长度和本轮是否被采用。

再使用目录实际返回的标识读取正文：

```json
{
  "action": "read",
  "snapshotId": "<目录返回的 snapshotId>",
  "version": "<目录返回的 version>",
  "itemId": "<目录返回的 itemId>",
  "offset": 0,
  "limit": 1600
}
```

正文每页最多 4,000 字符。若返回 `truncated: true`，使用同一 `snapshotId`、`version`、`itemId` 和返回的 `nextOffset` 继续读；不要自行猜测页码或把第一页当成全文。

目录与正文读取都不调用模型、不修改记忆，也不执行附件。角色取得证据后再决定是否需要进一步回忆或行动。它仍可使用原有长期记忆搜索、问题回忆或源插件查询，但这些属于另一个检索范围。

## 会话、版本与有效期

- 工具根据宿主执行上下文中的会话身份授权，不能通过参数指定别人的会话。其他会话即使知道快照编号，也不能读取其内容。
- `version` 校验的是快照内容。旧快照可能仍可读取，但会标明它不是当前快照；不会悄悄替换成新版内容。它也不能证明底层文件、记忆或活动此刻仍未变化。
- 快照缺失、被淘汰或版本不符时，工具返回明确状态。此时应重新列目录或读取源插件，不得声称已经读取原文。
- 快照只保存在当前插件实例的有界内存中；默认总容量 8 MiB、最多 64 份快照。达到容量约束后旧快照会被淘汰；单轮资料过大而无法完整保存时，会明确显示不可用，不承诺精确取回。
- 插件卸载或重载会注销工具并清空快照。旧工具引用也返回 `disposed`，不会在停止后继续读取。重启后需要新的组装才能建立快照，原有长期存储不受影响。

快照保存的是文字。**检索到图片说明、路径或音频描述，不代表已经看过图片或听过音频。** 需要核对图像细节时仍应读取对应原始媒体，并区分“查到记录”“媒体已进入输入”和“已对当前问题分析媒体”。

## 窗口不足时的处理

之前在组装阶段直接抛出容量错误，会让后续自动压缩失去运行机会。本次将这种压力改成可观察的状态：

1. 撤下本轮可选资料与放不下的目录提示，保留必需资料。
2. 记录 `pressure.state: awaiting-compaction`，区分主要来自历史的 `history` 与仅靠压缩历史无法解决的 `non-compressible`。
3. 正常返回组装结果，让宿主继续进入 `agent/pre-step` 和既有模型请求路径。
4. 观察到请求进入 `llm/stream` 时标记 `request-observed`；是否压缩成功以既有引擎回执为准。

预算层不会自行再发起一套压缩，不会删除历史，不会更改工具调用配对。本机 billion-context 接管了压缩入口，并停用了 DSH 原生的另一套自动压缩；此次修改**不恢复原生第二套压缩**。本地接线路径仍由既有引擎负责历史范围、事务提交和失败回执。

这并不保证任何超长请求都能成功。如果系统提示、工具定义和回复预留本身就超过窗口，压缩历史也可能无济于事，宿主最终容量错误仍会保留。下游组装错误和规划期间模型切换也不会被预算层当成普通窗口压力吞掉。

## 设置页可以核对什么

`contextBudgets` 状态按会话记录当前模型、窗口来源、回复预留、剩余空间、模型建议总量、实际采用量和各来源理由，并显示：

- 实际采用与未采用的资料数，以及目录、线索所占的估算量。
- 快照是否可用，目录是否注入，模型选择了多少条按需读取线索。
- 当前是 Gemini 规划还是本地降级，以及降级原因。
- 容量压力是等待宿主处理，还是已经进入请求路径。

“快照已保存”“目录已注入”和“进入请求路径”分别是不同阶段，均不等同于角色已经阅读全部资料，也不等同于压缩已完成。

## 验证范围

本次新增的回归使用合成内容和临时目录，不写正式记忆、不发送 QQ、不请求外部模型，也不启动正式 DSH：

- `test/context-budget-pressure.test.js` 按已核对的宿主顺序模拟组装、`agent/pre-step` 和既有 `llm/stream` 压缩入口，覆盖巨型工具结果、规划期间历史增长、不可压缩内容超限，以及真正下游错误继续传播。
- `test/context-recall-host.test.js` 使用实际 `createHost`、临时 `LifeEngine`、正式注册的工具和共享服务，验证三方资料汇集、被省略内容按目录分页精确读取、跨会话拒绝，以及卸载后的失效行为。
- `test/context-recall.test.js` 与预算单元回归验证快照容量、版本、分页及预算选择等基础约束。

这些结果证明本地实现和接线契约，并不代替真实提供方验收。Gemini 在正式请求中如何分配、角色是否主动选择正确的回忆条目、真实长会话能否完成压缩与继续回复，仍需结合对应运行回执或单独真实调用确认。
