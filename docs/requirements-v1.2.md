# 岑舒日常生活、随机事件与心情行为联动模块需求文档

**版本：** V1.2  
**项目名称：** `dsh-cen-shu-life`  
**运行环境：** DSH Desktop  
**角色依据：**《岑舒_第七版.json》

## 一、开发目标

开发一个独立的 DSH 插件，让岑舒拥有持续的日常生活、随机事件、事件进度和由心情驱动的行为模式。

插件根据角色卡中的作息、工作、兴趣、性格、人际关系和行为规则，维护岑舒的生活状态，并结合 `dsh-feiyu-mood` 的真实心情数据，决定她在当前对话中应采用的行为模式。

本项目采用轻量化实现，优先复用 DSH 现有能力和已安装插件，不修改 DSH 核心代码，不重复开发已有功能。

### 1.1 插件职责

- `dsh-speak-up`：负责随机主动聊天的触发。
- `dsh-feiyu-mood`：负责心情判断、数值变化和历史记录。
- `dsh-cen-shu-life`：负责日常生活模拟、随机事件、事件进度、心情与行为模式映射，以及动态上下文注入。

三个插件应保持职责独立，通过现有接口或只读适配器协作。

### 1.2 核心目标

1. 岑舒的日常生活能够随时间持续推进。
2. 随机事件能够发生、持续、发展并自然结束。
3. `dsh-feiyu-mood` 的心情变化能够转化为符合角色卡的具体行为。
4. `dsh-speak-up` 触发聊天时，岑舒能够结合当前生活、近期事件和行为模式自然开口。
5. DSH 重启后，重要生活状态和进行中的事件仍然存在。

## 二、技术可行性与实现原则

### 2.1 已有技术基础

根据现有项目源码，`dsh-feiyu-mood` 已具备以下能力：

- 使用 `state.json` 保存心情状态。
- 记录整体心情值和七种情绪维度，包括开心、踏实、甜蜜、心疼、担心、难过和吃醋。
- 保存最近一次心情变化的原因、可信度和更新时间。
- 通过 DSH 的 `systemPrompt.context` 机制向模型提供动态心情上下文。
- 提供 `/dsh-feiyu-mood/state` 状态路由，并支持选择相应的心情记录。

相关源码：

- [dsh-feiyu-mood](https://github.com/Yuuyuko-uu/dsh-feiyu-mood)
- [DSH 系统提示词模块](https://github.com/deepseek-ai/deepseek-harness/tree/main/packages/core/system-prompt)

DSH 提供的动态上下文机制可以作为本插件向模型传递生活状态和行为规则的主要方式。

### 2.2 必须在开发前确认的接口

正式开发前，检查当前实际安装的 DSH 和 `dsh-feiyu-mood` 版本，确认：

1. 插件入口、依赖注入和生命周期接口。
2. 动态上下文注册及注销方式。
3. 心情状态的实际字段、会话标识和多份心情的对应关系。
4. `/dsh-feiyu-mood/state` 路由的调用方式、访问权限及返回结构。
5. 插件的本地数据目录和定时任务机制。

不得仅凭接口名称推断调用方式。需要以实际源码、安装版本和运行测试为准。

### 2.3 心情数据读取方案

按以下顺序选择实现方式：

1. 优先使用 `dsh-feiyu-mood` 已提供且允许插件调用的状态接口。
2. 如果接口无法被其他插件可靠调用，使用只读文件适配器读取其实际保存的 `state.json`。
3. 如果数据缺失、格式不兼容或会话无法匹配，则降级到角色卡的平常行为模式，并记录错误。

文件适配器必须检查数据格式和版本，处理文件不存在、读取失败及数据更新过程中的异常。

严禁修改或覆盖 `dsh-feiyu-mood` 的心情数值、情绪维度和历史记录。

### 2.4 实现边界

本项目不需要修改 DSH 核心，不需要单独部署数据库或外部服务，也不需要训练新的模型。

日常生活、事件进度和行为模式可以通过本地状态文件、规则判断及动态上下文实现。

模型能够根据明确的行为指令提高角色表现的一致性，但无法保证每次生成都完全符合规则。因此，必须通过实际对话测试验证效果。

## 三、日常生活模拟

### 3.1 生活规律

依据角色卡维护岑舒的一天、一周和一年中的生活规律，包括：

- 工作日的起床、上班、午休、下班、回家和睡前活动。
- 周一容易烦躁、周五晚上较放松、周六逛旧书摊、周日晚上可能因家里的电话而低落等倾向。
- 下雨天、回南天、季节变化、春节、发工资和出远门前后的行为倾向。
- 档案馆工作、旧书、纪录片、租房生活及家庭相关的小事。

以上规则作为行为倾向和事件触发条件使用，不得强制每次发生。

插件根据真实日期、时间、星期和已保存状态判断岑舒当前可能正在做什么。默认时区为 `Asia/Shanghai`，允许修改。

### 3.2 随机事件库

事件分类包括：

1. 工作事件，例如扫描老照片、遇到难辨认的文字、临时加班。
2. 个人生活，例如阅读、整理房间、感冒、楼下修路。
3. 兴趣活动，例如逛旧书摊、淘到一本书、看纪录片。
4. 周期性事件，例如周末活动、家庭电话和节假日回家。
5. 出行事件，例如出门前准备、抵达某个地方和旅途中遇到的小事。

每个事件模板至少包含：

- 唯一 ID 和事件名称。
- 事件分类。
- 触发条件、适用时段和随机权重。
- 持续时间或结束条件。
- 可选的后续阶段。
- 冷却时间和重复限制。
- 可选的心情影响提示。

事件模板应使用 JSON 保存，便于后续直接编辑和扩充。

### 3.3 事件生命周期

事件状态采用以下流程：

`待触发 → 进行中 → 已结束`

多阶段事件需要记录当前阶段。例如，一本书可以经历刚买到、读到一半、继续阅读和读完等阶段。

要求：

- 事件状态保存在本地，重启后继续有效。
- 事件根据时间、预设条件或聊天中获得的信息推进。
- 已结束的事件不得重新作为同一件新事件触发。
- 事件可以持续数小时或数天。
- 过期事件按规则结束，不得无限保留。
- 同时最多保留两件主要的进行中事件，数量可以调整。
- 每日新事件默认最多两件，允许调整。
- 允许某些日子没有新事件。

事件必须符合岑舒的背景和日常生活，不得持续制造重大事故、戏剧性冲突或无依据的经历。

## 四、心情与行为模式联动

本节属于强制实现要求。

### 4.1 心情数据与行为模式分离

`dsh-feiyu-mood` 负责产生和保存心情数据。本插件负责把心情数据转换为符合角色卡的行为模式。

不能仅将“当前心情：低落”注入上下文。每种模式都必须提供明确的行为规则，至少涉及：

- 回复长度与信息量。
- 语气、标点和用词。
- 主动找话题及提出问题的倾向。
- 对青枔的关心、玩笑、夸奖和感情话题的回应方式。
- 角色专属称呼和口头习惯。
- 当前模式下需要减少或避免的行为。
- 模式进入、维持和退出的条件。

### 4.2 行为模式映射

实际映射必须以《岑舒_第七版.json》的具体人物设定为准。以下为首版规则框架。

| 心情信号或情境 | 行为模式 | 行为要求 |
|---|---|---|
| 开心明显上升，且整体心情高于基线 | 很高兴 | 话量增加，可以连续说几句，感叹号增多，偶尔连续发消息或表情包 |
| 开心或甜蜜适度上升 | 有点高兴 | 更愿意聊天，偶尔主动询问青枔的情况 |
| 踏实程度较高，没有明显冲突情绪 | 平常放松 | 正常接话，保持原有的嘴损、较真和称呼习惯 |
| 难过明显上升或整体心情持续偏低 | 低落 | 回复变短，减少语气词和表情包，不强行表现高兴 |
| 心疼或担心上升，且青枔遇到困难 | 心软 | 优先关心青枔的具体情况，减少抬杠和玩笑 |
| 甜蜜上升，且对话涉及夸奖或暧昧 | 难为情 | 回复变短，回避直接承认心事，可能自然换话题 |
| 吃醋上升，且对话涉及相关感情话题 | 吃醋后收声 | 可以问一两句，随后减少话量，不直接承认吃醋 |
| 生活状态或日程显示疲惫 | 累 | 减少话量，不强行延长对话，第二天能够自然接续 |
| 工作事件或具体互动表明烦躁 | 烦 | 减少玩笑和表情包，避免把坏情绪转嫁给青枔 |
| 对话中发生明确冒犯 | 被惹到 | 句子完整，句号增多，语气可能客气得过头；不无休止争吵或翻旧账 |
| 青枔认真表达喜欢或直接询问感情 | 慌 | 允许短暂回避或停顿，随后根据角色设定认真回应，不无限期躲避 |
| 青枔难受、半夜表达想念或需要陪伴 | 心软优先 | 即使岑舒自己低落或烦躁，也优先回应青枔的需要 |

疲惫、烦躁、被惹到和慌张等状态没有对应的独立心情维度时，应结合日程、生活事件和当前对话判断。

### 4.3 心情判定规则

不得将心情插件的数值档位直接等同于人物的行为状态。

判定时应综合参考：

1. 整体心情相对基线的变化。
2. 七种情绪维度及其变化幅度。
3. 最近一次心情变化的原因和可信度。
4. 当前生活事件和日程。
5. 当前对话的实际内容。
6. 角色卡规定的行为条件。

轻微的心情变化不应导致模式频繁切换。明显且可信的变化应及时生效。

例如，整体心情下降不能直接认定岑舒烦躁；甜蜜上升也不能在缺少相关情境时直接认定她难为情。

各项阈值、持续时间和优先级应可配置，默认值通过测试调整。

### 4.4 行为模式优先级

当多个条件同时满足时，按以下顺序处理：

1. 角色卡规定的必要行为和安全要求。
2. 青枔明确需要关心时，优先回应其需要。
3. 明确的感情相关情境，例如表白、直接询问感情。
4. 明确的难为情或被惹到情境。
5. 疲惫、烦躁等生活状态。
6. 根据心情数据选择基础行为模式。
7. 无明显触发条件时，使用平常模式。

优先级只用于解决模式冲突，不得覆盖角色卡中的明确禁忌。

### 4.5 动态上下文注入

每轮目标会话请求模型时，插件应根据最新数据生成简短的行为指令。

示例：

```text
【当前行为模式：低落】

依据：最近一次可信的心情变化显示难过程度上升。

行为要求：
回复变短，减少语气词和表情包。
不要强行表现得高兴。
青枔询问时，可以简短说出自己的情况。
保持岑舒原有的口吻和称呼规则。
```

上述示例仅用于说明格式，实际内容必须根据当前数据动态生成。

要求：

- 通过 DSH 支持的动态上下文接口注入。
- 每轮优先读取最新有效状态。
- 只向绑定岑舒的会话注入。
- 不重复注入完整心情历史和无关事件。
- 不强制角色直接宣布自己的心情。
- 不覆盖原始角色卡、系统提示词或聊天历史。
- 读取失败时降级到平常模式。

### 4.6 心情更新时序

`dsh-feiyu-mood` 在一轮对话结束后判断并记录心情变化。因此，新心情通常从下一次符合条件的模型请求开始影响回复。

本插件必须遵守这一机制：

1. 不尝试追溯修改已经生成的回复。
2. 下一轮请求开始时重新读取最新有效心情。
3. 如果心情插件尚未完成本轮判断，则继续使用上一份有效状态。
4. 不得为了加快更新而重复触发心情判断或修改其内部状态。
5. 心情自然恢复时，应允许行为模式逐步回归平常。

### 4.7 模式持续与退出

每次模式切换时记录模式名称、选择原因、触发时间和最近更新时间。

模式持续时间由情绪强度和对应情境决定。条件解除后，应逐渐恢复平常模式，避免相邻两轮无故反复切换。

当前模式不能仅因一次轻微波动立即退出，也不能在触发条件消失后永久保留。

## 五、事件与聊天的关系

本插件负责维护事件，不直接发送聊天消息。

事件发生后，插件将事件及其进展加入动态上下文。模型可以在合适的聊天时机自然提起。

要求：

- 事件发生不等于必须立即告诉青枔。
- 记录事件最近一次被提及的时间。
- 同一件事不得在连续几轮中反复提起。
- 用户询问相关内容时，优先依据事件记录回答。
- 不得编造没有对应记录的既往经历。
- 不得强制每次主动开口都汇报生活状态。
- 当前行为模式应影响事件的表达方式。

例如，很高兴时可以多说几句，低落时可能只提一句，难为情时可能提到一半便换话题。

主动聊天的触发仍由 `dsh-speak-up` 处理。

## 六、状态与数据存储

所有数据默认保存在本地。

建议数据目录：

`<DSH_HOME>/cen-shu-life/`

默认使用 DSH 家目录；如果设置了 `DSH_HOME`，应遵循该环境变量。不得假定所有安装都使用同一个硬编码路径。

文件包括：

- `config.json`：插件设置。
- `profile.json`：生活规律和行为限制。
- `events.json`：事件模板库。
- `state.json`：当前生活状态、事件进度和行为模式。
- `history.json`：近期事件、提及记录和结束记录。
- `diag.log`：运行、事件触发、模式切换及异常日志。

原始《岑舒_第七版.json》和 `dsh-feiyu-mood` 的数据均保持只读。

数据格式应包含版本号，支持后续升级。

## 七、设置页面

提供独立的「岑舒生活」设置页面。

首版包括：

1. 总开关。
2. 目标会话绑定。
3. 时区设置，默认 `Asia/Shanghai`。
4. 事件检查间隔，默认 30 分钟。
5. 每日新事件上限，默认两件。
6. 同时进行的事件上限，默认两件。
7. 事件分类开关。
8. 随机事件概率。
9. 动态上下文开关。
10. 心情联动开关。
11. 行为模式映射和阈值设置。
12. 心情数据读取状态。
13. 当前行为模式及触发原因。
14. 生活状态和事件进度预览。
15. 手动新增、结束和重置事件。
16. 模拟心情与事件的测试功能。

测试必须使用独立的模拟数据，不得修改真实心情记录。

设置修改后应尽可能立即生效。确实需要重启的项目应明确提示。

## 八、分阶段实施计划

为控制开发复杂度，按以下顺序实施。

### 阶段一：生活引擎

实现本地配置、日程规则、随机事件库、事件生命周期和持久化存储。

验收要求：事件可以生成、持续、推进、结束，并在 DSH 重启后保留有效状态。

### 阶段二：心情适配与行为模式

接入 `dsh-feiyu-mood` 的实际数据，完成会话匹配、心情读取、行为模式判定和动态上下文注入。

验收要求：模拟不同心情后，目标会话能够读取对应状态，并获得正确的行为指令。

### 阶段三：实际对话测试与调整

使用固定测试情境检查不同模式下的实际回复，调整阈值、优先级、持续时间和提示词。

验收要求：行为模式能够稳定影响回复长度、语气、标点、主动性和回应策略，同时保留岑舒的人物特征。

阶段之间应保持独立，便于定位问题。阶段三完成后再决定是否增加更丰富的设置页面和事件模板。

## 九、测试与验收

### 9.1 生活事件测试

- 能够根据时间和概率生成事件。
- 事件能够持续、推进和结束。
- 重启后，进行中的事件仍然存在。
- 同一事件不会频繁重复。
- 已结束事件不会被误认为新事件。
- 事件内容符合角色卡背景。

### 9.2 心情与行为测试

至少测试以下情形：

- 开心上升时，回复明显更活跃。
- 轻度开心时，更愿意聊天，但不会过度兴奋。
- 难过上升时，回复长度、语气和标点发生相应变化。
- 心疼或担心上升且青枔遇到困难时，优先关心青枔。
- 吃醋上升且出现相关话题时，表现出克制。
- 甜蜜上升且出现夸奖或暧昧情境时，表现出难为情。
- 疲惫、烦躁、被惹到和慌张可以由对应条件触发。
- 心情恢复后，行为模式逐步恢复平常。
- 数据读取失败时，不伪造心情，也不永久锁定某种模式。

**验收必须检查实际生成的回复。** 只检查日志中出现了模式名称，不能视为通过。

### 9.3 插件协同测试

- 心情更新后，下一次符合条件的模型请求能够读取最新状态。
- `dsh-speak-up` 触发主动聊天时，能够使用最新生活状态和行为模式。
- 不重复开发主动聊天触发器。
- 不重复执行心情判断。
- 不覆盖心情历史或原始角色卡。
- 其他角色的会话不受影响。

### 9.4 故障恢复测试

- 心情插件停用时，生活模拟仍可独立运行。
- 心情数据缺失或格式变化时，安全降级并记录日志。
- 配置文件损坏时，能够提示错误并尽可能恢复默认配置。
- 插件卸载时，不删除原始角色卡和心情数据。
- 定时检查不得重复生成事件或无限积累后台任务。

## 十、后续扩展

第一版仅实现生活状态、随机事件、事件进度、心情行为映射和基础设置。

后续可增加：

- 从聊天中提取考试、面试、生日等重要日期。
- 根据对话结果更新事件阶段。
- 更精细的心情与行为模式映射。
- 更丰富的事件模板和周期规则。
- 事件、心情与行为模式的可视化回放。

这些功能不属于第一版验收范围，不得阻碍基础功能安装和运行。

## 十一、最终验收目标

岑舒拥有持续更新的生活状态和随机事件。即使暂时没有新消息，她的生活事件也可以按时间推进。

当 `dsh-speak-up` 触发聊天时，她能够结合当前生活、近期事件和最新有效心情自然开口。心情变化通过独立的行为映射层影响实际回复，且始终以《岑舒_第七版.json》的性格、行为和关系设定为准。

整个项目应保持轻量、独立、可调试、可扩展，不修改 DSH 核心，不破坏现有插件和角色数据。
